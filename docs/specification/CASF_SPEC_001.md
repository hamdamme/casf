# CASF Project Specification
**Cryptographic Audit and Signing Framework**
Implementation baseline for a solo developed open source Python applied research project
Version 0.9 • 10 October 2026 • Status: design review draft
This specification defines what to build, the bytes to authenticate, the assumptions required for each security claim, and the evidence required before a release. It is intended for the project owner and any contributor working one bounded task at a time. Documentation precedes implementation. No CASF application code has been implemented as part of this document.
Executive overview. Build a small Python library, a command line verifier, a SQLite store, and a separate reference witness service. Sign every record with Ed25519, link records using SHA 256, and submit sequential checkpoints to one independently operated, stateful witness. Verification must report record validity, external anchoring, freshness, and trust separately. A successful verification is not proof that every real world event was recorded.
Delivery boundary. The requested source file, Cryptographic_Audit_Framework_Technical_Documentation.docx, was not accessible when this draft was prepared. Early design notes supplied secondary context for the initial design. The original document was later located and reconciled in the [source reconciliation record](D01-source-reconciliation.md), which records D01 as closed. Section 3 retains the initial comparison context; this specification is not a tracked changes revision of the original file.
Source reconciliation status. The [source reconciliation record](D01-source-reconciliation.md) closes D01 and adopts CASF SPEC 001 revision 0.9 as the governing baseline. Protocol approval, fixture review, and milestone completion require their own evidence. Treat the witness as a separate administrative trust domain, even when the research demonstration runs on one computer.
The intended contribution is a reproducible evaluation of a constrained audit design. Hash chains, signatures, transparency logs, and external witnesses are established ideas. CASF does not presently establish a new cryptographic construction, a literature gap, or superiority over existing systems.

## 1 Project charter
CASF will provide an embeddable mechanism for producing and independently checking audit histories. The problem is that ordinary stored logs can be edited, reordered, or restored to an older valid snapshot without reliable evidence in the restored copy itself. CASF addresses integrity evidence and conditional detection of missing history; it does not make storage physically immutable.
The primary users are Python application developers, operators responsible for retaining audit evidence, and researchers studying integrity and availability tradeoffs. The initial use case is a local application that records administrative actions, exports an evidence bundle, and lets a separate verifier check it without access to the application’s private signing key.
Objectives. Produce an explicit interoperable byte format; verify the complete retained sequence; maintain external checkpoint evidence; expose failures without converting uncertainty into success; and measure cost and detection coverage under controlled attacks. The project should remain understandable and maintainable by one developer.
Deliverables. A versioned protocol, Python package, CLI, SQLite adapter, reference witness service, verification fixtures, adversarial suite, reproducible benchmark runner, threat model, operator guide, disclosure policy, and research report. The independent verifier must work from an exported bundle with only public trust material. Online freshness checking is a separate operation.
Success criteria. Every mandatory rule maps to an automated test or an explicitly manual operational check. Valid vectors produce identical bytes and digests across supported environments. Expected detectable attacks fail verification; attacks outside the model produce documented limitations, not exaggerated success claims. A clean environment can reproduce the benchmark procedure and recover a crashed append without ambiguity about what committed.
The project does not promise a publication, certification, minimum throughput, or production security. Release decisions depend on evidence, not a calendar. Schedule estimates in Section 24 are planning aids for part time solo work.
## 2 Scope and non goals
Included in version 1. One ordered log per immutable manifest; one Ed25519 record and checkpoint key per log; one pinned witness identity per log; per record signatures; sequential verification; root authorized manifests; rotation through linked log epochs; bounded JSON input; deterministic export; idempotent appends; checkpoint submission and receipt retrieval; online witness queries; backup and restore procedures; synthetic workload evaluation.
Excluded from version 1. Distributed writers, consensus, blockchain anchoring, Merkle inclusion proofs, Byzantine witness quorums, public gossip networks, forward secure evolving keys, trusted hardware, native HSM or cloud KMS integration, arbitrary signature algorithm negotiation, confidential payload storage, general purpose timestamp authority, a web dashboard, regulatory compliance claims, and enterprise multi tenant administration.
HMAC is excluded from the public verification protocol. A party able to verify an HMAC generally holds the secret needed to create one, which does not serve the intended public verification boundary. If a future application needs an HMAC for a separate private workflow, it must use distinct keys and a separate profile. CASF signatures do not provide legal nonrepudiation by themselves.
Integration contract. An application decides which events to emit and authenticates its users. CASF records the supplied actor identifier as an assertion by the application; it does not authenticate that actor. A signature means an authorized key signed bytes, not that the event occurred or that its description is accurate.
Atomicity boundary. A business database update and a CASF append are not one atomic transaction. Applications requiring reliable delivery SHOULD write an outbox entry in the same transaction as the business change, then relay it with a stable event ID. A relay crash can cause a retry; it must not duplicate the logical event. A missing or malicious outbox producer remains outside CASF’s completeness guarantee.
Retention is full history in version 1. There is no redaction or pruning protocol. Sensitive data should be excluded or replaced with application managed opaque references before append. A digest of a predictable secret is not anonymization.

## 6 Threat model and trust boundaries
Assets are authenticated record bytes, ordering, checkpoint and receipt history, private keys, pinned public trust configuration, witness high water state, and availability of evidence. Confidentiality of plaintext payloads is not a CASF cryptographic guarantee.
| Adversary | Capabilities | Expected boundary |
|---|---|---|
| Storage attacker | Edit, delete, reorder or restore writer files | Cannot forge uncompromised signatures; old valid prefixes need an external reference |
| Compromised writer | Control process, event content and online log key | Can sign false new events and alternative unwitnessed histories |
| Network attacker | Delay, drop, replay or reorder exchanges | Can cause unavailability; cannot forge pinned signatures |
| Malicious witness | Lie, equivocate, lose state or sign old state | Single witness assurance fails if its honesty or durability fails |
| Compromised verifier | Replace code, trust keys or pinned state | Outside the guarantee; local output is no longer reliable |
| Compromised authority | Authorize attacker keys and manifests | Identity and future trust fail; retained historical evidence needs separate assessment |

Boundary A, application to library. Event fields are untrusted input. The library validates encoding and shape, not truth. Boundary B, writer to storage. SQL constraints improve consistency but do not make a hostile administrator trustworthy. Boundary C, writer to witness. The witness independently verifies submitted records and must have different credentials, durable storage, and an administrative failure domain. Boundary D, evidence to verifier. Bundled keys are data until matched to separately provisioned trust. Boundary E, verifier to trust state. Root pins, witness pins, policy serials, and high water marks must survive rollback independently of the evidence being checked.
Assumptions A1 through A6 are explicit: A1 cryptographic primitives and implementations behave as intended; A2 the verifier and its trust material are intact; A3 the required witness is honest and does not roll back its retained state; A4 the verifier can contact that witness for online claims; A5 the relevant evidence is available; A6 key provenance and compromise status are accurately provisioned. A single host demo does not establish administrative independence.
No guarantee covers events never submitted, maliciously chosen payloads, destruction of all evidence, indefinite network partitions, or cryptanalytic breaks. Clock values are assertions, not proof of real time.
## 7 Security guarantees and limitations
| Claim | Required conditions | Explicit limitation |
|---|---|---|
| Detect changed signed bytes | A1, A2, trusted signing key | Does not establish truthful content |
| Detect interior removal or reordering | Full expected sequence or trusted endpoints, A1 and A2 | An isolated valid record does not prove surrounding completeness |
| Detect rollback below an anchor | Retained trusted checkpoint and corresponding history comparison | A self contained old valid bundle alone cannot reveal rollback |
| Detect divergence from witnessed history | A1 to A3 and compare extension to the witness state | An unobserved private branch may remain undetected |
| Establish current witness view | A1 to A4 and nonce bound response within query timeout | Says nothing about events withheld from the witness |
| Resist rewriting a witnessed prefix after writer key theft | A1 to A3 and access to the retained anchor | Does not prevent false future records or preserve availability |

Per record signatures allow public origin checking under a pinned key. Hash chaining binds a specific sequence. Witnessing adds an external retained reference. These are separate properties. A local checkpoint stored beside a rollbackable database adds no independent rollback protection.
Two clients using the same honest durable witness cannot both obtain witness acceptance for incompatible extensions of that witness’s accepted prefix under this protocol. This is conditional branch exclusion at that witness, not global consensus. Different witness configurations, witness rollback, or a malicious witness invalidate that statement. Detecting a malicious witness’s split views requires clients to compare evidence; a general gossip protocol is outside version 1.
A fixed Ed25519 private key is not forward secure. An attacker holding it may sign alternative old records. The external checkpoint constrains what can match an already retained prefix, but does not make the compromised key itself forward secure. Revocation cannot identify the exact moment a key was stolen from unauthenticated timestamps.
Unwitnessed exposure. The suffix after the last accepted checkpoint can disappear or be rewritten by a compromised signer without contradicting that checkpoint. A configured checkpoint period is an operating target, not a hard maximum loss window. Delayed workers, overload, outages, and crashes can extend the exposure indefinitely. Report the actual pending count and duration where observable.
## 8 Architecture and component contracts
The primary data path is application → validation → canonical body → hash and signature → SQLite commit → checkpoint outbox → remote witness → signed receipt. The verification path is evidence bundle plus independent trust → strict parser → sequence and signature verifier → checkpoint comparison → optional online witness query → structured report.
| Component | Responsibility | Must not do |
|---|---|---|
| model and canonical | Strict schemas, canonical byte production | Infer missing signed fields |
| crypto | Domain encoding, SHA 256, Ed25519 adapters | Implement elliptic curve arithmetic |
| writer | Sequence allocation, idempotency, checkpoint creation | Report remote acceptance before a receipt |
| storage | Transactions, constraints, consistent snapshots | Serve as a trust anchor by itself |
| verifier | Pure verification of streams and anchors | Require a private key or writable log database |
| witness | Validate extensions, retain head, sign receipts | Accept a greater count without checking the extension |
| trust | Pins, signed status statements, retained high water state | Trust a key merely because it came in a bundle |
| CLI | Stable commands and machine reports | Print secrets or collapse uncertainty to success |

Use explicit interfaces: Signer.sign(message) returns 64 signature bytes; PublicVerifier.verify(key, signature, message) either succeeds or raises a typed error; Store.append_transaction(request) returns the committed envelope; WitnessClient.submit(proposal) returns a verified receipt; TrustStore.resolve(manifest_hash) returns an explicitly configured decision. Inject clock, random source, and transport for deterministic tests, while production randomness comes from the operating system.
The reference witness is a separate process with a separate database and witness key. A local development mode may use loopback, but reports and benchmarks must label that mode. Transport security and service authentication protect access and privacy; signed protocol objects remain necessary because TLS does not preserve evidence after export.
Dependency direction is CLI and adapters → application services → protocol and interfaces. Core verification must not import HTTP server code or the writer implementation. Sharing tested cryptographic primitives is acceptable; fixture generation must not merely call the same end to end writer path as the verifier test.
## 9 Canonical serialization and primitive profile
CASF uses JCS from RFC 8785 [1], encoded as UTF 8 without a byte order mark. Object property order follows JCS; ordinary Python sorted key JSON is not an interchangeable implementation. Unicode normalization is not performed. Parsers reject duplicate property names and invalid Unicode. The RFC defines serialization; CASF additionally restricts the accepted application data model below.
CASF data profile. Objects have string keys; values are strings, booleans, null, arrays, objects, or integers in the inclusive range minus 9007199254740991 through 9007199254740991. Floating point values are forbidden throughout, including payloads. Wire number tokens containing a decimal point, exponent, or negative zero are rejected even if their value is integral. Python booleans must not pass integer field validation. Larger integers, decimal amounts and binary content must be represented by application defined strings.
Version 1 rejects unknown protocol fields at every fixed schema boundary. The payload and attributes objects may contain arbitrary profile conforming keys. Required fields are never supplied by parser defaults. All size limits apply before expensive cryptographic operations: canonical record body at most 65536 bytes, nesting depth at most 16 containers, each string at most 32768 UTF 8 bytes, and wire record envelope at most 131072 bytes. Containers count the body as depth 1. Invalid input produces no signature or append. Every protocol timestamp uses the exact UTC format and calendar constraints in Section 11. Every index is a nonnegative safe integer; index exhaustion forbids another checkpoint and requires a new epoch.
Primitives and encodings. H is SHA 256 with a 32 byte output. Ed25519 is the pure variant in RFC 8032 [2], not Ed25519ph. Use the maintained cryptography library [10], with a reviewed pinned version; do not implement the primitive. Public keys are raw 32 byte values; signatures are 64 bytes. Binary fields use unpadded base64url with canonical reencoding checks. Digests are exactly 64 lowercase hexadecimal characters. IDs are lowercase UUID strings except key IDs, which are digests.
In the following pseudocode, J(x) means the canonical bytes, || means byte concatenation, hex(x) is lowercase hexadecimal, raw(x) decodes a digest, and Z is 32 zero bytes. Domain strings are literal ASCII followed by exactly one zero byte, written as \x00. No newline follows a domain. All digest and signature inputs below are bytes, never the printable hexadecimal digest unless explicitly stated.
## 10 Manifest and trust bootstrap
Each log has an immutable authority signed manifest. It selects one signing key and one required witness for that log’s lifetime. A verifier MUST obtain the authority public key and expected authority key ID through an authenticated channel separate from the evidence bundle. Trust on first use is not the default. A root signed manifest authorizes a key; it does not prove that the authority is the identity the user intended.
The manifest body has exactly these fields: version=1; type="manifest"; log_id; issuer_id; log_key_id; log_public_key; witness_id; witness_public_key; created_at; predecessor. issuer_id and witness_id are derived key IDs. created_at uses the timestamp format in Section 11 and is informational. predecessor is null for an initial log, or the exact object {log_id, manifest_hash, final_checkpoint_hash, final_receipt_hash} for a rotated epoch. UUID log_id is generated from a secure random UUID version 4 source.
key_id(pk) = hex(H(b"CASF/v1/key-id\x00" || pk))
M = H(b"CASF/v1/manifest\x00" || J(manifest_body))
manifest_sig = Ed25519.Sign(authority_sk,
b"CASF/v1/manifest-sign\x00" || M)
genesis = H(b"CASF/v1/genesis\x00" || M)

The manifest envelope is exactly {body, manifest_hash, signature}; body contains the manifest body, manifest_hash is hex(M), and signature is base64url. The log public key must derive log_key_id and the witness public key must derive witness_id. Manifest validation includes the authority signature and an exact match to the expected log identity. A replacement manifest for the same log_id is rejected.
Witness endpoints are local transport configuration, not trust identities. Changing a URL is permitted if the pinned witness key stays the same and authenticated transport is maintained. Changing the witness key requires a new log epoch in version 1. The reference witness registers manifests through a local administrator command before accepting submissions; an arbitrary remote caller cannot register a new root or log.
Before the first record, store the manifest and genesis transactionally. Before claiming witnessed status, register and submit an initial checkpoint. No trust is inferred from an empty directory, a database filename, or an environment supplied key URL.
The local trust configuration is a version 1 JSON object with fields version, authorities, logs, and policy. authorities maps issuer_id to base64url public key. logs maps expected log_id to an object containing manifest_hash, witness_id, witness_url, and minimum_status_serial. policy contains mode, allow_unwitnessed, query_timeout_seconds, and max_chain_steps. Reject duplicate keys and unknown fields. Administrative provisioning, not a bundle import, authorizes this file. Store observed checkpoint and status high water marks in a separate atomic local state file keyed by manifest_hash; use locking for concurrent verifiers. A bundled status statement is accepted only if its authority signature verifies and its serial is at least the provisioned and observed minimum. Missing required status evidence yields UNKNOWN trust. Initial provisioning includes an active statement with serial 1. Neither offline nor online witness mode claims that independently distributed revocation information is globally current.
## 11 Record schema and append protocol
| Body field | Type and constraint |
|---|---|
| version and type | Integer 1 and literal "record" |
| log_id and manifest_hash | Exact manifest UUID and digest |
| seq | Integer from 1 through 9007199254740991 |
| event_id | Lowercase UUID, stable for logical retries |
| recorded_at | UTC string YYYY-MM-DDTHH:mm:ss.ffffffZ |
| actor and event_type | Nonempty strings, at most 256 UTF 8 bytes each |
| payload and attributes | Objects in the CASF data profile |
| prev_hash | Genesis digest for seq 1; previous record_hash otherwise |
| key_id | Exact log_key_id from the manifest |

The body contains all listed fields and no others. UTC timestamps must be calendar valid with seconds 00 through 59; leap second notation is rejected. Sequence order, not clock order, defines log order. The caller supplies actor, event_type, payload, attributes, and event_id. The writer generates recorded_at on first successful append. Original source time may be an application string in attributes; CASF does not trust it as chronology.
D_i = H(b"CASF/v1/record\x00" || J(body_i))
S_i = Ed25519.Sign(log_sk,
b"CASF/v1/record-sign\x00" || D_i)
record_envelope = {"body": body_i,
"record_hash": hex(D_i), "signature": b64url(S_i)}

Sign the domain plus the raw digest using pure Ed25519. The signature is not inside its own hashed body. The next body binds the previous record digest; each signature must still be verified independently. Verifiers reject a wrong key, incorrect digest, missing field, noncontiguous sequence, wrong log binding, or invalid signature. Unknown algorithms and versions never fall back to weaker behavior.
Idempotency. Define the request object as exactly {event_id, actor, event_type, payload, attributes}. Store its digest H(b"CASF/v1/request\x00" || J(request)) with the record. Repeating event_id with the same request digest returns the original record and timestamp. A different digest returns EVENT_ID_CONFLICT. Neither a retry nor a conflict consumes a sequence. Per log event IDs are unique; this does not establish exactly once behavior for a business action across unrelated systems.
## 12 Checkpoint objects and production
A checkpoint commits to the entire prefix through count. Its body has exactly version=1, type="checkpoint", log_id, manifest_hash, index, count, head_hash, previous_checkpoint_hash, key_id, issued_at, and final. index starts at 0 and increments by 1. count is a nonnegative safe integer. head_hash is genesis for count 0, otherwise the record digest at count. key_id is the manifest’s log key. final is a boolean.
C_j = H(b"CASF/v1/checkpoint\x00" || J(checkpoint_body))
Q_j = Ed25519.Sign(log_sk,
b"CASF/v1/checkpoint-sign\x00" || C_j)
checkpoint_envelope = {"body": checkpoint_body,
"checkpoint_hash": hex(C_j), "signature": b64url(Q_j)}

For index 0, previous_checkpoint_hash is hex(Z), count may be 0 through 128, and the extension begins at genesis. Later checkpoints reference the immediately preceding accepted checkpoint digest. count never decreases; an increase is at most 128 records. A same count checkpoint is permitted for a heartbeat or final seal, but its head must remain unchanged. issued_at has the record timestamp format and is only the writer’s time assertion.
The writer maintains at most one pending checkpoint per log. It selects a committed prefix in a consistent snapshot and stores the signed checkpoint and exact extension range in a durable outbox before network submission. It MUST NOT issue the next checkpoint until the current receipt is validated and stored. Appending records may continue while a nonfinal checkpoint is pending. Retries reuse identical checkpoint bytes.
The initial operating target is a checkpoint after 128 pending records or 60 seconds since the last accepted checkpoint, whichever first triggers while the worker runs. When idle, a 60 second heartbeat with unchanged count is allowed. Large backlogs drain in batches of at most 128. These are defaults to measure, not security guarantees.
A final checkpoint MUST cover the entire committed local head. seal_log requires no pending checkpoint and at most 128 unwitnessed records; otherwise return PENDING_DRAIN and drain normal checkpoints first. Recheck these conditions under the append write lock. Seal the local log in the same transaction that creates the final checkpoint. No subsequent append is allowed even if the witness is offline. Verification rejects any records beyond a supplied final checkpoint. Receipt acquisition may be retried. Abandoning a pending checkpoint and inventing a different one with the same index is forbidden; recovery rules in Section 18 apply.
## 13 Witness acceptance and receipt protocol
The required witness is a stateful verifier, not merely a timestamp signer. It receives the checkpoint envelope and all complete record envelopes from its retained count plus 1 through the proposed count, in order. This simple version exposes event payloads to the witness. Operators must consent to that data boundary and minimize sensitive fields. A future digest only or Merkle protocol requires a new reviewed design.
Acceptance sequence. Authenticate the caller, enforce body limits, resolve the preapproved manifest, and validate the checkpoint signature. In one serialized per log transaction, load the retained head and checkpoint index. If an identical checkpoint was previously accepted, return its stored receipt. Otherwise require the next index, exact previous checkpoint digest, nondecreasing count, and at most 128 new records. Validate every record according to Section 11, beginning with the retained head. Require the calculated final digest to equal head_hash. A sealed log accepts only retrieval of an already stored receipt.
The witness must retain, at minimum, the immutable manifest, current count and head, current checkpoint index and digest, sealed state, every accepted checkpoint and receipt, and accepted record digests indexed by sequence. Complete record bodies may be discarded after successful validation and commit. Retaining digests permits diagnostics but is not a recoverable record backup. Never log request bodies by default.
Receipt body fields are exactly version=1, type="receipt", witness_id, log_id, manifest_hash, checkpoint_hash, checkpoint_index, count, head_hash, previous_receipt_hash, and accepted_at. The first receipt references hex(Z); subsequent receipts reference the prior receipt digest. All checkpoint related values match the accepted checkpoint. accepted_at is witness asserted UTC, not a certified timestamp.
R_j = H(b"CASF/v1/receipt\x00" || J(receipt_body))
W_j = Ed25519.Sign(witness_sk,
b"CASF/v1/receipt-sign\x00" || R_j)
receipt_envelope = {"body": receipt_body,
"receipt_hash": hex(R_j), "signature": b64url(W_j)}

Create the receipt inside the state transaction, store it with the checkpoint and updated head, durably commit, and only then return it. A crash before commit produces no accepted state; a crash after commit returns the same receipt on retry. Never acknowledge from an uncommitted in memory head. A conflicting proposal is rejected with CONFLICT and safe evidence identifiers; preserve signed conflicting checkpoints for investigation where policy allows.
## 14 Witness transport and online freshness
The reference HTTP service exposes POST /v1/logs/{log_id}/checkpoints, GET /v1/logs/{log_id}/receipts/{checkpoint_hash}, and POST /v1/logs/{log_id}/latest. The submit JSON object has exactly {checkpoint, records}. Receipt lookup returns the stored checkpoint and receipt. Missing logs and missing receipts return distinct 404 codes. Submission returns 201 on first acceptance and 200 on an identical retry. Validation failures use 400, authentication failures 401 or 403, state conflict 409, oversized input 413, throttling 429, and transient service failure 503.
Nonloopback deployments MUST use HTTPS with normal certificate validation and authenticated submit access, preferably mutual TLS via a reverse proxy. Read access must also be authenticated if metadata is sensitive. A configured bearer credential is acceptable for the reference service only over HTTPS; never put it in a URL or command line. Errors returned by CASF contain exactly {code, message, retryable} as JSON; no stack traces, payloads, keys, or tokens. Set a 16 MiB request limit, 128 record limit, 10 second total client timeout, and bounded service concurrency. Exact retry bytes are safe; automatic redirects to different origins are forbidden.

**HTTP error boundary (approved 2026-10-24).** Requests handled by CASF return JSON errors containing exactly {code, message, retryable}. Existing CASF status codes remain unchanged, including 429 when witness processing capacity is exhausted. Requests rejected by the HTTP server before reaching CASF may receive a minimal plain text response. Examples include 400 for malformed HTTP and 503 when the server connection limit is reached. Neither response may expose credentials, record payloads, private keys, stack traces, or internal implementation details. Server resource limits remain required. This exception to the JSON response requirement is recorded in [ADR-004](../adr/ADR-001-through-004-baseline-decisions.md#http-error-boundary-amendment).

For a latest query the verifier generates a fresh random 32 byte nonce and sends exactly {nonce}, base64url encoded. The witness reads its committed state and signs a response body containing version=1, type="latest", nonce, witness_id, log_id, manifest_hash, checkpoint_hash, receipt_hash, checkpoint_index, count, head_hash, final, and responded_at. The accompanying response includes the matching checkpoint and receipt. Before any accepted checkpoint, return NO_CHECKPOINT without a success assertion.
L = H(b"CASF/v1/latest\x00" || J(latest_body))
latest_sig = Ed25519.Sign(witness_sk,
b"CASF/v1/latest-sign\x00" || L)
response = {"body": latest_body, "signature": b64url(latest_sig),
"checkpoint": checkpoint_envelope, "receipt": receipt_envelope}

The verifier validates all signatures, identities, matching digests, nonce and state fields. The response must arrive within the configured 10 second monotonic elapsed time budget. Never reuse a nonce. A timeout or partition is INCONCLUSIVE, not evidence of rollback. A fresh response proves the witness signed this view during the query under its honesty assumption; it does not prove the writer has disclosed every committed record.
## 15 Verification algorithm and result semantics
Full verification begins with independently trusted authority and witness pins, expected log identity, and the caller’s mode: integrity, anchored, or online. It validates the manifest, trust status, all fixed schemas, and resource limits. It then streams records from sequence 1, checks exact sequence increments and predecessor digests, recomputes record digests, and verifies signatures using the manifest key. Empty histories use genesis. Export metadata never overrides computed values.
For anchored mode, validate the checkpoint signature and pinned witness receipt, and establish that the supplied history reaches its count with the exact committed head. A shorter history is INCOMPLETE relative to that anchor. A different digest at the anchor is DIVERGENT. Extra valid records form an UNWITNESSED suffix. These labels describe evidence, not the intent of an attacker. Verify supplied checkpoint and receipt chains as well; a directly trusted pinned checkpoint can serve as the start of an incremental check.
Online mode additionally fetches the fresh response in Section 14 and compares it to both the evidence and locally retained high water state. A lower checkpoint index than a retained trusted index, or a different digest at the same index, is a WITNESS_STATE_CONFLICT. A newer index requires the intervening checkpoint and receipt chain to be supplied or retrieved by the client before advancing the local pin. Receipt lookup by checkpoint hash permits walking previous hashes backward; reverse and validate the chain with an explicit work limit. Exceeding that limit is INCONCLUSIVE until more evidence is obtained.
Incremental verification. Starting from a trusted checkpoint, validate only the contiguous suffix. Report verified_from and verified_through; do not label unexamined bodies as individually signature checked. A historical checkpoint can be authentic without being current. A witness receipt commits to accepted content but does not supply missing record bodies.
The report has independent fields: protocol_status, signature_status, chain_status, trust_status, anchor_status, freshness_status, verified_from, verified_through, witnessed_through, unwitnessed_count, checkpoint_hash, first_failure_seq, and diagnostic_codes. Allowed status values must come from documented enums, never ad hoc prose. The overall result is PASS only when every predicate required by the requested mode succeeds and no trust status is unknown. A machine report always includes the mode and assumptions used.
Integrity PASS means only the supplied sequence is structurally valid under accepted trust. Anchored PASS also requires every supplied record to be within the selected anchor or an explicit allow_unwitnessed option; when allowed, report PARTIAL_ANCHOR visibly. Online PASS requires a fresh witness view and evidence through that view, and rejects an unwitnessed suffix unless explicitly allowed. It never means real world completeness.
Report enums are fixed for version 1: protocol_status is VALID, INVALID, or UNSUPPORTED; signature_status and chain_status are VALID, INVALID, or NOT_CHECKED; trust_status is TRUSTED, UNKNOWN, REVOKED, or CONFLICT; anchor_status is NONE, MATCHED, PARTIAL_ANCHOR, INCOMPLETE, or DIVERGENT; freshness_status is NOT_REQUESTED, FRESH_WITNESS_VIEW, INCONCLUSIVE, or CONFLICT. overall is PASS, FAIL, or INCONCLUSIVE. NOT_CHECKED is not success. Counts and sequence positions are nonnegative safe integers or null when not established; first_failure_seq is null for nonrecord failures. An empty valid log reports verified_from=0 and verified_through=0. diagnostic_codes is an array of stable uppercase strings. Format errors map to INVALID, unsupported profiles to UNSUPPORTED, proven mismatches to FAIL, and missing trust or unavailable required evidence to INCONCLUSIVE; revoked trust is FAIL. CLI exit categories in Section 19 retain their more specific codes.
## 16 Key lifecycle and compromise response
Use distinct Ed25519 keys for the offline authority, each log epoch, and the witness. Generate them using a library backed by operating system randomness. Derive key IDs from raw public keys using Section 10. Public keys are not secrets. Private keys must not enter the database, export bundles, fixtures, repository, logs, or command line arguments. Test keys must be visibly labeled and never accepted in release deployment examples.
The reference provider stores encrypted PKCS8 PEM using the cryptography library’s supported encryption helper. Obtain the passphrase from an interactive hidden prompt or an inherited file descriptor supplied by a secret manager. Restrict the key directory to its owner and use atomic creation without overwriting existing files; validate restrictive file permissions or the platform ACL equivalent. Encryption at rest does not protect an unlocked key from a compromised process. Python cannot promise secure memory erasure; document this limitation. Exact encryption encoding must be recorded in compatibility tests, not described as a new CASF protocol.
Normal rotation. Version 1 rotates by closing the old log and creating a new log_id with a new manifest and log key. Obtain the old final checkpoint and witness receipt, then place their digests in the new manifest’s predecessor object. The authority signs the new manifest. The new witness registration validates that predecessor evidence, including final=true, against trusted old keys. Sequence numbers restart at 1 for the new log. Verification across epochs checks every link. Within log key replacement is prohibited.
Emergency response. Stop the affected writer, preserve evidence, revoke trust in the affected key or log, and recover from an independently retained checkpoint. If a final seal cannot be safely obtained, create a new root authorized log with predecessor=null and explicitly document a discontinuity outside the cryptographic continuity claim. Do not manufacture a final receipt, backdate a revocation, or silently rewrite the old manifest. Reestablish trust through an authenticated administrative channel.
A root signed status statement has body fields version=1, type="status", issuer_id, serial, manifest_hash, status ("active" or "revoked"), issued_at, and reason. Sign H(b"CASF/v1/status\x00" || J(body)) under domain b"CASF/v1/status-sign\x00". Envelope fields are {body, signature}. serial is a positive safe integer per manifest; retain the largest observed serial outside the log store. Revocation is terminal for that manifest. Offline verification reports the statement serial used and cannot claim it is the latest. By default, revoked history is cryptographically inspectable but not trusted; any historical exception requires a separately approved pinned anchor policy. Authority rotation is manual reprovisioning in version 1.
## 17 Storage and concurrency
SQLite is the initial storage adapter. Proposed tables are manifests(log_id primary key, manifest_hash unique, envelope); records(log_id, seq, event_id, request_digest, envelope, record_hash); heads(log_id primary key, count, head_hash, sealed); checkpoints(log_id, index, checkpoint_hash, envelope, state); receipts(checkpoint_hash primary key, envelope); and outbox(log_id primary key, checkpoint_hash, from_seq, to_seq, attempts, next_attempt_at). Use unique(log_id, seq), unique(log_id, event_id), unique(log_id, index), foreign keys and exact length checks. Store canonical UTF 8 envelope bytes as BLOBs; indexes are derived lookup data, not authenticated facts.
Append transaction. Validate and copy the request before locking. Use BEGIN IMMEDIATE. Check sealed state and event ID idempotency, read the committed head, allocate count plus 1, construct and sign the body, insert the record and request digest, update the head, and COMMIT. Return success only after commit. If commit outcome is uncertain, require lookup or retry with the same event ID. Do not retry with a new ID. Sequence overflow seals further appends and requires a new epoch.
Writers serialize through the database; a process mutex alone is insufficient. Use one connection per executing thread or a dedicated writer thread, a 5 second busy timeout, and no more than three bounded retries with jitter on lock contention. Return BUSY after the deadline. Signing occurs within the transaction for the initial local provider; a slow remote signer would require a new concurrency design. Do not call the witness while holding a writer transaction.
Use WAL mode, synchronous=FULL, and foreign_keys=ON; verify the effective settings at startup. SQLite provides one concurrent writer and snapshot behavior in WAL mode [8]. WAL is unsuitable for multi host network filesystem access [9]. Host filesystem and hardware behavior remain part of the durability assumption. Choose a maintained SQLite build and review current upstream advisories at release time; do not freeze an unverified bundled version.
Checkpoint and export reads use a consistent transaction snapshot. Database triggers may prevent accidental update and delete, but must not be described as protection against a file administrator. Startup MUST compare stored heads with verified records and external evidence before resuming after restore or suspected corruption. Full startup verification is the version 1 default; future acceleration needs an authenticated anchor and explicit scope reporting.
## 18 Crash recovery backup and retention
The writer distinguishes COMMITTED_LOCAL, PENDING_WITNESS, and WITNESSED. A caller that requests witnessed completion may receive a local commit followed by a witness timeout. Return the committed record identity and pending state; never imply that a timeout rolled back the append. Business workflows must decide whether pending evidence is acceptable. No cross service atomic transaction is promised.
On restart, retry the exact pending checkpoint. If the witness accepted it but the local receipt write failed, receipt lookup recovers it. If the witness is ahead of the local checkpoint journal, obtain and verify the intervening chain. Reconcile it with local records before proceeding. If the necessary committed records were lost in a local restore, stop writing and report RESTORE_BEHIND_WITNESS. Reusing the same sequence with newly signed content is forbidden. A manual recovery may recover records from backup or start a documented discontinuous epoch.
Create backups through SQLite’s consistent backup facility or a quiesced snapshot procedure that includes required WAL state. Copying only the live main database file is not an approved procedure. Store backups and trust anchors in distinct administrative locations, verify a restored copy before promotion, and record the manifest, last witnessed checkpoint, package version, and backup creation information. Protect private key backups separately. A witness digest store cannot reconstruct lost payloads.
The witness must not resume signing after a restore if it cannot establish that its high water state is at least as new as all previously acknowledged receipts. For the reference deployment, keep an independently retained backup of accepted state and reconcile against client receipts; if completeness of recovery cannot be established, retire the witness identity and create a new epoch. This operational assumption is not solved by ordinary SQLite durability alone.
The witness uses the same authority status rules as a verifier when accepting submissions. Installing a verified revocation blocks further acceptance for that manifest; old checkpoint and receipt retrieval remains available. Status distribution is an authenticated administrative operation in version 1. A witness that has not received a revocation may still sign, so verifier policy must independently check status. Ordinary signing key rotation does not imply that an old key was compromised.
Retention preserves full records, manifests, public keys, checkpoints and receipts for the project’s chosen retention period. There is no safe deletion command that preserves full record verifiability in version 1. Destruction of plaintext or keys is an operator lifecycle action with explicitly reduced guarantees. Avoid claiming cryptographic erasure or compliance based on file deletion. Recovery drills must include disk full, corrupt backup, lost key, writer rollback, witness rollback, and unavailable witness.

## 20 Evidence bundle and compatibility
The version 1 bundle is a directory, avoiding automatic archive extraction. Required files are manifest.json, records.jsonl, checkpoints.jsonl, receipts.jsonl, and export.json. Optional public status statements belong in status.jsonl. Trust pins are supplied separately. Each JSONL line is one canonical envelope followed by one LF; no blank lines or byte order mark. records.jsonl is ordered by seq; checkpoints and receipts are ordered by checkpoint index. Empty histories have an empty records file.
export.json has exactly version=1, type="export", log_id, manifest_hash, through, record_count, and generated_at. through and record_count both equal the count exported from sequence 1. Export metadata is informational and unsigned; the verifier must recompute its claims and reject mismatches. Including a receipt cannot authenticate missing record bytes. Export may include a pending signed checkpoint but no invented receipt. A report marks it as locally signed only.
Export creation uses a temporary sibling directory, writes and flushes all files from one snapshot, then renames to the requested destination without overwriting. Symbolic links and nonregular files are rejected on import. Do not follow bundle supplied filesystem paths or fetch embedded URLs. Impose a 128 KiB maximum JSONL record line and configurable total record and evidence object budgets; stream records without loading the entire file. Protocol object bodies other than record bodies are limited to 16 KiB. Checkpoint chain traversal defaults to 10000 steps per online check and can be explicitly raised for large histories.
Portable data format compatibility is separate from Python API compatibility. Protocol version 1 objects must preserve their interpretation across package releases. Unknown fields in fixed bodies are errors; extensions require a new version or a separately specified application payload. The verifier must not silently discard unfamiliar fields before signature checking.
Database migrations are transactional, versioned, backed up, and tested against published fixture stores. They may rebuild indexes but must never reserialize or rewrite authenticated historical bodies. A new cryptographic profile starts a new log epoch. Provide a read only old profile verifier for the documented support window; do not downgrade a new profile to make it pass an old verifier.
## 21 Tests and adversarial matrix
Every case below requires a reproducible fixture and an assertion on the specific result code. “Detect” means the verifier or witness rejects the altered evidence under the stated configuration, not that CASF prevents the attacker from modifying storage.

|---|---|---|
| T01 | Duplicate keys, floats, NaN, exponent integers, invalid UTF 8, lone surrogate | Reject before signing or verification |
| T02 | Unicode key ordering, control characters, nested arrays, safe integer edges | Exact canonical bytes; out of bounds rejected |
| T03 | Alter body, digest or signature; wrong key; wrong domain | Invalid signature or digest |
| T04 | Delete middle record, reorder, duplicate seq, wrong genesis or cross log splice | Chain or binding failure |
| T05 | Verify offline export on clean machine with public keys only | Same report as reference fixtures |
| T06 | Concurrent writers and repeated same event ID | One logical record; contiguous committed sequence |

Use unit tests for schemas and domains, property based tests for serialization and sequence mutations, process level tests for crashes and SQLite contention, and HTTP integration tests for witness state transitions. Fuzz parsers with a bounded corpus and store minimized failures as regressions. Every protocol rule must have a positive and a relevant negative example.
Conformance vector package. Freeze full JSON bodies, canonical byte hex, public test keys, record digests, signatures, checkpoints, receipts, nonce responses and expected reports. Include empty log, one record, two records, heartbeat, seal, rotation, and all malformed cases. Generate expected results using a reviewed fixture builder and cross check canonicalization against an independent conforming implementation; verify signatures against RFC test vectors [2]. This document defines byte rules, but does not fabricate uncomputed hex vectors. Producing and reviewing those vectors is a mandatory M1 gate.
No claims of formal proof or penetration testing may be made from this suite. Release tests must also exercise failure modes that correctly remain undetectable, so the documentation cannot drift into stronger promises than the experiment supports.
## 22 Benchmark and applied research methodology
Research questions. RQ1: Which rollback and fork scenarios become detectable when a local signed chain gains independent witness state? RQ2: What latency, throughput, storage and network cost does that witness add? RQ3: How do checkpoint batching and outages change observed unwitnessed exposure? RQ4: What operational burden and implementation complexity does the constrained approach impose on a solo maintained project?
Compare A, a hash chain without signatures; B, a signed chain with only local checkpoints; and C, the same signed chain with the external witness. These are experimental configurations, not equally secure deployment profiles. Keep canonical bytes, payloads, storage durability, hardware and batching comparable. Report signature cost separately from witness cost. A Merkle variant may be a later exploratory comparison; it is not necessary to finish version 1.
Hypothesis H1 is that C detects restoration below the witness state when the witness remains honest and reachable, while an isolated B cannot distinguish the same old valid snapshot from its original history. H2 is that larger checkpoint batches reduce per record witness overhead while increasing the pending suffix under comparable loads. H3 is that network outages increase time to witnessed completion and may prevent a freshness conclusion. These are hypotheses to test, not current measured results.
Use synthetic events with canonical body targets near 256 bytes, 1 KiB, 8 KiB and 64 KiB, adjusting payload padding after accounting for fixed fields. Do not label an impossible 256 byte total body as a valid workload; if metadata exceeds that target, report the actual minimum. Test 1000, 100000, and 1000000 records where hardware permits; 1, 2, 4 and 8 producer processes; checkpoint batches of 1, 32 and 128; local and separate host witnesses; and injected RTTs of 0, 10, 50 and 200 ms with controlled loss or outage intervals. A million maximum size records may be expensive; record resource exclusions in advance.
Measure local append latency and witnessed completion latency separately, p50/p95/p99, committed records per second, full and incremental verification time, CPU time, peak RSS, database and export bytes per record, witness retained bytes, bytes transferred, backlog size, and detection delay from attack injection to verification result. Capture failed operations and retries as outcomes, not discarded samples.
Use a fixed seed list, warm up each configuration, randomize run order, and execute at least 10 independent measured runs per primary configuration. Use run level summaries and bootstrap 95 percent confidence intervals across runs; do not treat millions of correlated records as independent replications. Report the distribution and practical effect size. Record OS, CPU, RAM, disk, filesystem, Python, SQLite, crypto library, dependency lock, commit, settings, dataset seed and command.
## 23 Research validity and reproducibility
Separate cryptographic reasoning, adversarial observations, and performance results. Correctness tests can demonstrate implementation behavior on selected cases; they do not prove universal security. Performance experiments do not establish attack resistance. Report false negatives only for attacks that the declared assumptions predict should be detectable, and explicitly label out of model or unobserved attacks.
Detection experiment. Start from a seeded valid history, retain a witness checkpoint, make a controlled copy, inject exactly one mutation, and invoke a named verification mode. Record which keys and stores the attacker controls, which anchor the verifier has, whether online connectivity is available, and the expected result before running. Repeat at the beginning, middle, last witnessed record, and unwitnessed tail. Compare the observed result with the predeclared expectation matrix.
Validity controls. CPU scaling, disk caches, SQLite synchronization, background load, event size distribution, network emulation, warm up, and key provider choice can confound performance. Fix or report them. Local witness runs underestimate independent deployment cost. Synthetic workloads may not represent production audit patterns. Self authored code and self reviewed tests create assessment bias. Seek external review of the protocol and experimental design where possible; do not label that review as completed before it happens.
Release research artifacts under a documented license: workload generator, attack harness, configuration manifests, raw CSV or JSON measurements, analysis scripts, plots, environment capture, exact commands, and checksums. Use only synthetic data. An independent person should be able to reproduce the procedure without private keys or private services; public test keys must be clearly isolated from deployment keys.
The report must include unsuccessful runs, omitted configurations and reasons, limitations, and negative findings. Publish no table containing invented results or placeholder numbers that resemble measurements. Repository lines of code, dependency counts, deployment steps, and maintenance notes may describe complexity, but they are proxies rather than objective measures of usability or total cost.
If comparing external projects empirically, pin their versions, use their recommended secure configuration, and state differences in semantics. Do not compare CASF’s local asynchronous append with another system’s externally durable completion and call the result equivalent throughput. If a fair deployment is impractical, keep the comparison qualitative.

## 28 Decision register and remaining risks
| ID | Decision and proposed default | Closure point |
|---|---|---|
| D01 | Original source located and reconciled; see the [source reconciliation record](D01-source-reconciliation.md) | Closed |
| D02 | Approve one fixed witness and full record disclosure to it | Blocking M0 |
| D03 | Approve restricted JCS and pure Ed25519 domains; freeze vectors after review | Blocking M1 |
| D04 | Approve epoch based rotation and terminal log revocation | Blocking M0 |
| D05 | Select and review exact JCS, crypto and HTTP dependencies and runtime matrix | Blocking M0 |
| D06 | Choose witness operator, hosting, backup process and proof of administrative separation | Before any deployment claim |
| D07 | Confirm license, repository/package name and monitored security contact | Before public release |
| D08 | Set application retention and sensitive data policy | Before real data use |
| D09 | Select benchmark hardware and feasible large workload subset before runs | Before M7 |
| D10 | Decide supported release lifetime and capacity for external review | Before 1.0 |

D01 is closed according to the [source reconciliation record](D01-source-reconciliation.md). Other decisions and milestone conditions require their own approval and completion evidence; D01 closure does not establish those outcomes.
Residual risks include a compromised online writer, witness state rollback, loss of independently retained trust, incomplete source event capture, payload exposure at the witness, and the absence of an external security assessment. The proposed full record witness has linear bandwidth and verification work and is intentionally not a scale optimized transparency design. Long outage backlogs and full startup verification may be operationally costly; measure them before widening scope.
Future candidates include Merkle proofs, threshold witness policies, interoperable transparency formats, remote signing providers, privacy preserving commitments and forward secure signatures. Each changes the threat model or complexity and requires a separate proposal. None is implicitly included in version 1 or necessary to call the initial applied research complete.
